# План живой верификации Yogurt: agy, Porch и русский язык

**Версия плана: 1.0. Статус: план, а не отчёт о выполненных испытаниях.**

Целевая ревизия Yogurt — `b86893651f935e8eb151a8316701687da781d705`, ветка `feat/subscription-harness`. Контракт Porch — `b0c5cf4d5d236677595a508ee3491d56ae1e0e8a`. Перед выполнением нужно записать фактические SHA сборки, CLI и конфигураций; при изменении кода этот план становится основанием для регрессии, а не свидетельством проверки новой версии.

В рамках подготовки плана просмотрены исходники. **Новые запросы к провайдерам, запись микрофона, запуск GUI и испытания отказов не выполнялись. Все кейсы ниже имеют начальный статус `NOT_RUN`.** Предлагаемые диагностические средства ещё нужно реализовать. Изменения этой итерации — только документация.

## 1. Что именно требуется доказать

Проверять нужно всю цепочку: захват микрофона и системного звука → PCM → выделение речи → объединение фрагментов → WAV → выбранный CLI → модель → JSON → таймкоды встречи → SQLite → интерфейс → конспект → вопросы по встрече и библиотеке.

Приёмка относится к конкретной комбинации **сборка × ОС × версии CLI × профили × подтверждённая длительность встречи**. Успех одного профиля Porch не подтверждает все его backend. Успех короткого WAV не подтверждает часовую встречу.

Обязательные результаты:

1. Через оба заявленных маршрута фактически обрабатывается аудио, а не текст его описания; модель и effort проверены на максимально доступном уровне наблюдения.
2. Русская речь, особенно отрицания, короткие ответы, имена, суммы и даты, сохраняет смысл. Транскрипт не переводится самопроизвольно.
3. Фразы не исчезают и не дублируются на границах окон, пауз, пакетов, дорожек и сессий. Таймкоды совпадают с воспроизводимым аудио.
4. Долгая встреча не вызывает устойчивого роста очереди при штатной нагрузке; Stop, отмена и выход имеют предсказуемое завершение.
5. Успешный ответ CLI действительно сохраняется; ошибки и потеря части речи остаются видны пользователю после повторного открытия встречи.
6. Конспекты, заголовки, следующие шаги, переписывание, предложения папок, Ask и библиотека работают через выбранные текстовые профили без скрытого fallback и лишних запросов.

### Контракт текущего кода, который важно не перепутать

| Параметр | Реальное значение и следствие для испытаний |
| --- | --- |
| Аудио провайдера | Моно PCM16, 16 000 Гц; длительность `N / 16000`. WAV, создаваемый этим адаптером, занимает `44 + 2N` байт. |
| Окно выделения речи | 100 мс. Для выдачи фрагмента нужно минимум 3 голосовых окна; короткие «да/нет» требуют отдельной проверки. |
| Завершение по тишине | После 1 с тишины; в конце сохраняется до 200 мс тишины. Это добавляет собственную задержку до старта CLI. |
| Максимальный открытый фрагмент | 15 с; точка разреза ищется в последних 2 с. Реальная граница может оказаться примерно на 13–15 с. |
| Объединённый пакет | Пакет уходит, когда старейший ожидающий фрагмент дорожки старше 5 минут по времени встречи, и при остановке встречи. В пакете до 5 минут звука: паузы длиннее 1 с сжимаются до 1 с нулей, карта `parts` возвращает время на часы встречи. Неудачный пакет повторяется один раз через 5 с; прерванный — нет. Тайм-аут аудиозапроса не меньше 600 с. |
| Очередь | До 15 минут ожидающих PCM-сэмплов отдельно на дорожку; выполняемый запрос не входит в лимит. При переполнении удаляются старейшие ожидающие фрагменты. |
| Параллелизм | По одному ASR-запросу на дорожку одной встречи. Старые завершающиеся встречи могут сосуществовать с новой; глобального ограничения «всего два запроса» из этого не следует. |
| Сырые большие запросы | Адаптер отвергает фрагмент длиннее 15 минут. Нормальный путь приложения отправляет существенно меньшие пакеты; двухчасовая встреча не должна становиться одним WAV-запросом. |
| Таймкоды модели | Допуск до 1 мс за границей WAV — только допуск проверки чисел и округления, не обещание точности ASR до 1 мс. |
| Porch | И текст, и аудио идут через внутренний `backend_run.sh --mode media --raw`. Публичная команда `porch media transcribe` в этом маршруте не используется. |
| Конспект после ошибки | Завершившаяся очередь может содержать неудачные запросы. Конспект по сохранившейся части возможен и не доказывает полноту транскрипта. |
| Восстановление после перезапуска | Автоматического повторного ASR старого аудио нет. Сохранность аудио и честный статус незавершённости проверяются отдельно от возможного возобновления конспекта. |

Основания: [chunker](../app/src/main/asr/chunker.ts), [batch](../app/src/main/asr/batch.ts), [pipeline](../app/src/main/asr/pipeline.ts), [ASR-сессии](../app/src/main/asr/index.ts), [WAV](../app/src/main/asr/transcribe.ts), [harness ASR](../app/src/main/harness/transcribe.ts), [интеграция](../app/src/main/index.ts).

## 2. Уровни проверки и необходимые средства

| Код уровня | Что запускается | Что можно доказать |

| `C` | Настоящие CLI/Porch runner в изолированном окружении с управляемым отказом или подставным дочерним agy | Совместимость реальных промежуточных слоёв, нормализатора, путей и процессов. Реальный ответ модели этим не подтверждается. |

Один кейс может иметь несколько уровней. В отчёте результаты разделяются, например `A04/D: PASS`, `A04/E: NOT_RUN`.

### 2.1. Подготовить до расширенных live-прогонов

Следующие средства **запланированы, но сейчас не представлены как готовые команды или файлы**:

1. **Коррелируемый диагностический журнал JSONL.** Для каждого события нужны `runId`, `meetingId`, эпоха capture, дорожка, `chunkId`, `batchId`, `attemptId`, `requestId`; начало, число сэмплов и состав пакета; вставленные промежутки; enqueue/start/final/save/UI; причина отказа или отброшенный интервал. Время ожидания измерять монотонными часами.
2. **Наблюдатель CLI с прозрачной передачей данных.** Сохраняет разрешённые metadata, реальные пути и PID, argv, факт EOF stdin, типы событий, terminal status и exit code. Не меняет порядок байтов/событий. Проверить, что наблюдатель сам не задерживает запрос, не ломает EOF и отмену. Не сохранять весь environment, credentials или reasoning/thought deltas.
3. **Копия тестового WAV до очистки staging.** Для согласованных тестовых записей сохранять точный вход, SHA-256, число сэмплов и финальный ответ. Копия для проверки хранится отдельно; обычная очистка staging проверяется независимо.
4. **Управляемый replay и барьеры.** Выбор русских фикстур вместо существующих английских WAV, неравномерные размеры frames, паузы, ускоренная подача для переполнения, удержание конкретного CLI-ответа. Режим pass-through к живой модели явно отличать от подставного результата.
5. **Согласованный экспорт SQLite.** Через SQLite backup/транзакцию либо после остановки и checkpoint. Копии одного файла БД при активном WAL недостаточно. Включить встречи, все сегменты с `hidden`, notes, conversations, library sources, настройки и манифест аудио.
6. **Сравнение с эталоном.** Подсчёт WER, критических фактов, пропусков/дубликатов контрольных фраз, ошибок таймкодов, задержек и очереди. Отчёт должен показывать отдельные провальные записи, а не только среднее.

Существующий `TIMING asr` и внутренний `stats()` полезны, но не дают этой полной трассы. Временные WAV удаляются после запроса. Без дополнительных доказательств причина исчезнувшего слова может остаться неустановленной.

### 2.2. Зафиксировать среду

До первого live-вызова записать версии и SHA Yogurt/Porch/agy, ОС и архитектуру, реальный путь CLI после разрешения symlink, способ запуска из GUI/терминала, разрешения capture, аудиоустройства, частоты дискретизации, эффективные настройки приложения и точные профили Porch. Хешировать конфигурацию без секретов. Проверять на отдельном тестовом `userData` и согласованных записях.

Отдельно получить `agy models` и `porch media capabilities --json`. В форке запрашиваются `gemini-3.8-flash` и отдельный `--effort medium`, тогда как документация CLI показывает также полный slug `gemini-3.8-flash-medium`. Проверить, как именно установленная версия разрешает эту комбинацию. Нельзя считать поддержку alias доказанной по сходству названий или незаметно заменить модель ради прохождения теста; несовместимость фиксируется до длинного прогона.

**Отдельный Electron `userData` изолирует данные Yogurt, но не home/keyring, авторизацию и настройки CLI.** Для H02/H06/H09, конфликтующих настроек и изменения Porch config нужен отдельный пользователь ОС/VM либо документированно изолированное хранилище CLI с тестовым аккаунтом. До прогона подтвердить отсутствие в этой среде действующих API/ADC credentials. Не менять login/logout и постоянные настройки рабочего аккаунта.

Использовать штатный вход выбранного тестового аккаунта. Наличие ключей/ADC фиксировать только булевыми признаками; не копировать токены рабочего аккаунта. Условия допустимого использования выбранного тарифа и техническую доступность маршрута проверять отдельно. В [FAQ Google](https://antigravity.google/docs/faq) сторонние app wrappers описаны как неподдерживаемые на consumer plans; технический успех headless-вызова сам по себе не решает этот вопрос.

### 2.3. Что считать доказательством модели и подписочного маршрута

| Уровень | Свидетельство | Предел вывода |
| --- | --- | --- |
| Запрошено | `--model`, `--effort`, профиль и scoped env | Доказывает намерение приложения. |
| Сообщено CLI | Например, `init.model` и эффективная конфигурация CLI | Доказывает сообщение CLI; отсутствующий effort остаётся `unknown`. |
| Подтверждено сервисом | Доступные provider metadata, account usage или иной официальный diagnostic | Только этот источник позволяет усилить вывод о реальном исполнении и списании. |

Ответ модели «я Gemini», длина reasoning и скорость не являются доказательством модели/effort. Если доступны только argv, в отчёте писать «Flash/medium запрошены», а не «фактическая модель доказана».

Для direct agy проверить исключение API-ключей из дочернего окружения и действие session settings. Для Porch отдельно проверить авторизацию конкретного профиля: общую гарантию account-only на произвольные backend не переносить. При недоступности независимых billing-данных допустимый вывод — «работает через account auth без доступных API-ключей». Отсутствие мгновенно изменившейся суммы не доказывает невозможность другого списания.

## 3. Корпус реального аудио и эталоны

Ниже — задание на подготовку корпуса, а не утверждение, что такие записи уже созданы. Основу составляют настоящие человеческие записи; TTS и синтетические сигналы допустимы как дополнительные технические проверки.

| Фикстура | Содержание | Зачем |
| --- | --- | --- |
| `R01-native` | 15 с русской речи с новым случайным словосочетанием, произнесённым только в аудио | Доказать чтение звука. Сделать версии A/B одинакового формата с разным содержанием. |
| `R02-edge` | WAV ровно 2.000 с, речь близко к началу/концу; варианты длины ±1 сэмпл | Точный аудиочас, отсутствие перекодирования и padding. |
| `R03-short` | Естественные «да», «нет», «не надо», «пять» длительностью примерно 0.2/0.3/0.5 с | VAD не должен уничтожать смысловой ответ. |
| `R04-boundary` | 31 с непрерывной речи; контрольные слова около 13–15 с и в самом конце | Разрез внутри фразы, последний неполный 100-мс блок. |
| `R05-facts` | 90–120 с двух участников: «Алёна», «Север-17», 47 500 рублей, абсолютная дата, ответственный, отказ и исправление «не десять, двенадцать» | Русский, отрицания, числа, исправления, две дорожки. |
| `R06-mixed` | 25 с русской речи с английскими названиями/техническими терминами и умеренным шумом | Смешанный язык, имена и устойчивость к шуму. |
| `R07-silence` | 6–10 с цифровой тишины и отдельная запись комнатного шума без речи | Различить отсутствие речи, отсутствие вызова из-за VAD и ошибку модели. |
| `R08-natural` | 10–20 минут естественного разговора двух участников с ручной расшифровкой | Реалистичные паузы, перебивания, качество конспекта. |
| `R09-long` | 60 минут, затем 90/120 минут при заявлении такой поддержки; маркеры каждые 5 минут | Дрейф, очередь, квоты, память, полнота конца встречи. |
| `R10-library` | Три короткие встречи с разными проектами, датами, людьми и частично совпадающими словами | Scope, история Ask, ссылки на источники, отсутствие смешения. |
| `R11-context` | Длинная русская расшифровка с фактами в начале/середине/конце, кавычками, переносами и кодом | Бюджеты контекста 8192/16384/32768 и каскад конспектов. |

Для каждой записи создать манифест: SHA-256, источник/право использования, канал и sample rate, число сэмплов, способ преобразования в канонический PCM, ручной транскрипт, временные якоря, таблицу критических фактов. Для изменённого WAV сохранять родительский hash и преобразование. Для шумного варианта фиксировать способ смешивания и уровень шума.

Эталон строится по тому, что действительно слышно в записи, а не только по сценарию. Все критические факты и минимум 20% остальных фраз проверяет второй человек. Контрольное выражение native-кейса не должно попадать в prompt, словарь, filename или metadata, доступные CLI. Существующие английские E2E-WAV без ручного эталона подходят только для технического smoke: текст fake ASR не является расшифровкой этих файлов.

## 4. Аудио, длительность и таймкоды: 18 кейсов

В этой группе `P0` означает потерю/искажение содержания или времени, `P1` — качество и характеристику поддерживаемой нагрузки. В каждом кейсе сохранять вход, состав пакетов, сырой финал, SQLite-сегменты и результат сравнения с эталоном.

| ID / приоритет / уровень | Действия | Ожидаемый результат и доказательство |
| --- | --- | --- |
| **A01 · P0 · D+L** | Передать `R02-edge` через direct agy и Porch; отдельно варианты ±1 сэмпл. | Для 2 с — 32 000 сэмплов, 64 044 байта WAV. Hash канонического WAV совпадает между маршрутами; нет MP3-padding. Нельзя требовать, чтобы последний модельный сегмент закончился ровно в 2.000 с. |
| **A02 · P0 · L+E** | `R05-facts`, русский/auto, словарь с именами и дополнительным непрозвучавшим словом. | Имена, суммы, дата, отрицание и исправление сохранены; словарь не создаёт несуществующую речь. Транскрипт остаётся на языке записи. |
| **A03 · P1 · D+E** | Настоящий capture 44.1/48 кГц, mono/stereo, встроенный микрофон и гарнитура; отдельно системный звук. Локально разбить stdout helper посреди заголовка/сэмпла и объединить несколько frames в один read. | На ASR приходит 16 кГц mono без ускорения/замедления; транспортное разбиение не теряет и не повторяет сэмплы. Проверить правила выбора/смешивания каналов конкретной ОС, не предполагать их одинаковыми. Архив и транскрипт сверяются по waveform-маркерам. |
| **A04 · P0 · D+L+E** | Отдельно воспроизвести `R03-short`, включая содержательное «нет» между длинными репликами. | Ноль пропущенных смысловых ответов. Если PCM есть, а VAD не создал chunk, это потеря до модели. Порог 300 мс нельзя использовать для оправдания исчезнувшего решения. |
| **A05 · P0 · D+E** | Нажать Stop через 20/80/150 мс после последней фонемы; контрольный вариант — после 500 мс тишины. Варьировать размеры frames. | Последнее слово и его хвост сохранены. ### Четыре независимые шкалы времени

| Шкала | Как проверить |
| --- | --- |
| Исходный capture PCM | Время первого сэмпла, частота, число сэмплов, пропуски frames и эпохи helper. |
| WAV конкретного запроса | Длительность по сэмплам, начало chunk, вставленные нули; при Float32 → PCM16 учитывать документированное квантование и clipping. Hash Float32 не обязан равняться hash PCM16. |
| Относительные таймкоды модели | Валидация границ отдельно от реальной точности привязки слов к waveform. |
| Время встречи/архива и задержка обработки | Абсолютный offset, pause/resume и playback; задержки — монотонными часами. `Date.now` и видимая длительность UI не заменяют аудиочасы. |

Дополнительный локальный metamorphic-набор: один и тот же звук с ведущей тишиной; один результат с разными `startMs`; целая фраза и та же фраза на границе chunk; переставленный порядок завершения двух дорожек. Проверять инварианты содержания и времени, не требовать побайтово одинакового текста недетерминированной модели.

**Два риска, уже видимые при чтении кода.** `pipeline.give()` может отправить строки в UI после ошибки `save()`, поэтому скриншот не доказывает сохранение. `transcriptionPending` защищает состояние/аудио, но постоянная пометка неполноты после записи в просмотренном renderer не обнаружена. Это основания для E05/E06, а не заявление об уже выполненной runtime-проверке.

## 7. Долгая нагрузка и реальные ОС

### P01 — производительность одной дорожки

После коротких gates прогнать 10–20 минут настоящей речи через каждый основной маршрут. Измерять VAD-задержку, очередь, service time CLI, сохранение и UI отдельно. Сначала последовательные реплики, затем плотная речь. Ожидаемый темп — один запрос на дорожку примерно раз в 5 минут; фактическое число запусков проверять по журналу.

### P02 — обе дорожки и несколько завершающихся встреч

Повторить с двумя активными дорожками, затем E04. Снимать максимум/график процессов, RSS, глубину и возраст очереди по каждой встрече и суммарно. Условие штатной приёмки — ноль drops, отсутствие устойчивого роста backlog и корректное завершение всех jobs. Контролируемая задержка проверяет механику; ограниченный live-прогон — реальные service times.

### P03 — 60 минут, затем заявленный максимум

По 60 минут на каждый заявленный основной маршрут. Для обещания поддержки двухчасовых встреч — отдельный 120-минутный прогон каждого такого маршрута на основной ОС. Если выполнен только direct agy, в отчёте 120 минут подтверждены только для него. Проверить последние 5 минут и финальную фразу так же строго, как начало. Во время записи — один Ask и открытие старой встречи, чтобы проверить конкуренцию ASR/text.

### P04 — часы, архив и паузы

В изолированной VM дополнительно проверить изменение wall clock/сон–пробуждение, если заявлена работа через sleep. Реальный capture после сна, восстановление устройства и предупреждение о разрыве проверять отдельно. Задержки считать monotonic; дрейф оценивать после вычитания постоянной задержки захвата. Архивные M4A/Ogg сравнивать по декодированным якорям, а не требовать одинаковый hash с PCM WAV.

### P05 — установленная сборка и пути

Основная целевая ОС выбирается перед исполнением плана; это поле манифеста, не повод откладывать подготовку корпуса. На ней нужны все применимые P0, реальный microphone/system capture, GUI launch, permissions, реальный restart и установленная сборка. `electron-vite build` не заменяет native helper, упаковку и проверку DMG/EXE/AppImage.

| Платформа | Обязательный объём |
| --- | --- |
| Основная macOS или Linux | Полный план; direct agy и Porch; захват двух дорожек и настоящая установленная сборка. |
| Вторичная macOS/Linux, если заявлена | Smoke первого запуска, R05 → transcript → notes → Ask, permissions, GUI PATH, отмена/ошибка CLI, restart; один Porch-прогон. |
| Windows, если заявлена | Те же проверки для native `agy.exe`, включая завершение потомков и системный звук. Porch — отрицательный тест явного отказа. |
| Другая архитектура | Установка, capture и короткая полная AI-цепочка на реальном устройстве/ОС. |

### P06 — ресурсные ограничения и повторяемость

Сеть с задержкой/обрывом и отказ диска воспроизводятся в отдельной тестовой среде. Для нехватки места использовать выделенный ограниченный том либо инъекцию ошибки, а не заполнять общий диск. Наблюдать восстановление следующего явного запроса. Не вызывать массово реальные запросы ради quota failure. После остановки теста отдельно проверить отсутствие принадлежащих ему висящих процессов и временных файлов; локальное завершение не доказывает прекращение серверного расчёта.

## 8. Метрики и критерии приёмки

Ниже — **предлагаемые начальные пороги, не измеренные результаты**. Критерии сохранности фиксируются сразу. Пороги пользовательской задержки фиксируются после малого пилота и до большого прогона; менять их после неудачного результата без явного пересмотра требований нельзя.

| Метрика | Начальная цель | Как считать |
| --- | --- | --- |
| Сохранность контрольных фраз | 0 потерянных и 0 дублированных смысловых фраз | Сквозное соответствие исходного звука, отправленных WAV и сохранённых сегментов; учитывать hidden строки. |
| Критические факты | 100% правильных отрицаний, решений, чисел/дат и ответственных в размеченном корпусе | Таблица эталонных фактов; числовое значение независимо от записи словами/цифрами. Любой смысловой пропуск — отдельный дефект. |
| WER | Чистая речь ≤10%; заранее определённый шумный вариант ≤20% | Фиксированная Unicode/регистровая/пунктуационная нормализация. Отдельно имена/«ё»/отрицания/числа; micro и macro, результаты каждой записи. |
| Точность аудиочаса | Ноль неожиданно изменённых PCM-сэмплов после канонизации; математический offset ≤1 мс | Сэмплы, WAV header/hash, ожидаемые вставки нулей; Float32-квантование отдельно. |
| Привязка фраз | Медианная ошибка границы ≤300 мс, p95 ≤1 с | Ручные waveform-якоря. Пропущенные фразы не исключать молча: отдельно доля пропусков и число сопоставленных якорей. |
| Дрейф длинной записи | Дополнительный дрейф ≤100 мс за 60 минут после калибровки постоянной задержки | Начальный/промежуточные/конечный якоря каждой дорожки и расхождение между дорожками. |
| Штатная очередь | 0 dropped chunks, нет устойчивого роста возраста backlog | По дорожке, встрече и суммарно. Ограниченные синтетические overload-кейсы имеют другую ожидаемую приёмку. |
| Скорость обслуживания | Среднее `RTF_service < 1` на постоянно занятую дорожку; желательно ≤0.7 для запаса | `sum(serviceSeconds) / sum(submittedPCMSeconds)` в занятом интервале. Дополнительно речь/тишина/паузы: padding не должен скрывать медленную обработку. |
| Видимость финального текста | Предлагаемый ориентир p95 ≤30 с от конца контрольной реплики до сохранённого отображения | Раскладывать на VAD, queue, CLI, save и UI. Не считать эту цель обещанием до пилота. |
| Завершение после Stop | Предлагаемый ориентир p95 ≤120 с при штатной нагрузке | От Stop до полного transcript drain; генерацию notes измерять отдельно. Ошибки/timeout входят в отчёт, а не исключаются как неудобные измерения. |
| Отказ/отмена | 0 ложных успешных финалов, 0 callbacks после cancel, 0 неожиданных fallback | Terminal + процессы + БД + последующий запрос; controlled timeout/abort как в H10/H11. |
| Сохранность при ошибке | 100% тестовых ошибок сохраняют доступное исходное audio и правдивый статус | Playback, БД, reload, экспорт; частичные notes не скрывают неполноту. |
| Notes и Ask | Все критические решения/задачи сохранены, 0 выдуманных владельцев/дат/источников | Раздельно ASR-ошибки и ошибки текста; сначала notes по эталонному transcript, затем по настоящему ASR. |

Для предварительной оценки p95 собрать минимум 50 настоящих запросов на отдельно рассматриваемый маршрут/класс параллелизма, показывая `n` и распределение. Даже такая выборка описывает хвост приблизительно; она не подтверждает SLA. Несколько запусков дают отдельные измерения, не надёжный p95 или обещание 99.9% доступности. Повторить ключевые короткие аудиокейсы минимум три раза; точный текст может различаться, критические факты — нет.

Если настоящая модель регулярно выходит за длительность WAV, сохранить распределение overshoot и исходные ответы. Это повод разбирать контракт/модель и принимать отдельное решение, а не молча расширять 1-мс допуск до размера обнаруженной ошибки.

## 9. Порядок выполнения и бюджет реальных запросов

Один запуск CLI может включать несколько model turns и file-read calls. Считать отдельно **app jobs, CLI starts, model turns и usage**, если последний уровень наблюдаем. Timeout/maxTokens не являются денежным лимитом.

| Этап | Работа | Live-бюджет и условие перехода |
| --- | --- | --- |
| **G0: готовность** | Корпус, диагностика, D/C-проверки границ, H07/H08, сохранение/неполнота, процессы | 0 inference: только локальные части смешанных кейсов. Настоящие модельные попытки инструментов H05/H06 и успешный запрос после login H09 сюда не входят. P0-пробелы протокола/сохранности закрыть либо зафиксировать как блокеры; длинную нагрузку пока не начинать. |
| **G1: настоящий маршрут** | Короткий текст + `R01-native` каждым маршрутом | До 4 CLI starts. Подтверждены доступный auth route и чтение аудио; уровни доказательства модели явно указаны. |
| **G2: короткое аудио** | `R02-edge`, `R06-mixed`, `R07-silence` каждым маршрутом | Ещё до 6 starts, всего 10. Проверены точный WAV, русский и тишина. Первые 10 запусков передают около 96 с аудио суммарно; внутренние turns могут быть многочисленнее. |
| **G3: текст и контролируемые live-границы** | Ограниченные text chains, выбранные L-части H05/H06/H09/H11, второй text backend | Ещё до 12 starts на текст, до 4 на permission/deny/login/cancel, до 2 на иной backend, до 2 резервных. Начальный потолок — 30 starts; резерв не расходуется автоматически. Не поместившиеся ветки остаются непроверенными до расширенного бюджета. |
| **G4: основной короткий корпус** | 12 выбранных аудиовариантов × 2 маршрута × 3 повтора, по одному raw harness job на файл | Только при этом способе подачи ориентир равен 72 ASR starts. Через полный ASR pipeline бюджет рассчитывается по отдельному chunk/batch manifest: длинный файл создаёт несколько запросов. Raw-подача не заменяет VAD/E2E-кейсы. G1–G2 можно зачесть при полном совпадении условий. |
| **G5: сквозной пользовательский прогон** | 10–20 минут через native capture на каждом основном маршруте, E-кейсы и platform smoke | Число starts рассчитать по измеренной частоте chunks из G1–G4; ASR, notes/title/Ask имеют отдельные счётчики. Нужны все P0 по сохранности и переключениям. |
| **G6: длительность** | 60 минут, затем заявленные 90/120 минут; P01–P06 | Бюджет по фактическому среднему batch, числу дорожек и turns пилота, с оговорённым запасом. Не делить длительность встречи автоматически на 5 минут: у редкой речи пакеты короче. |

Ограничение количества запусков проверять до spawn. При неожиданном профиле, модели, API route, fanout, retry или достижении бюджета остановить прогон и сохранить доказательства; незавершённые кейсы пометить `ABORTED/BLOCKED`, не PASS. Намеренно не исчерпывать квоту и не обходить лимиты ротацией аккаунтов. Естественный 429 — полезное наблюдение, но не требование к нагрузочному прогону.

После исправления воспроизводимого дефекта: локальная регрессия по причине, три повтора затронутого короткого live-кейса и связанные выпускные gates. Не повторять весь дорогостоящий корпус без конкретного риска.

## 10. Выпускные ворота и отчёт

### Блокеры готовности

Следующее блокирует заявление «маршрут готов»: потерянная смысловая реплика/отрицание; смешение встреч/дорожек; повреждение или некорректное удаление audio; UI-успех при несохранённом результате; скрытая неполнота после reload; принятие ошибочного финала; неверный backend/account route; неожиданный fallback; неправильная шкала времени; штатное переполнение очереди.

**Правило для H03: два раздельных вердикта.** Выбор запрошенной модели/effort, отсутствие подмены и fallback — обязательный P0 функционального маршрута. Атрибуция фактического исполнения имеет отдельный статус для каждого уровня наблюдения. Если provider/CLI не раскрывает effort, этот пункт получает `NOT_OBSERVABLE`; функциональная приёмка маршрута возможна при остальных пройденных P0, но заявление «фактический medium подтверждён» заблокировано. Допустимая формулировка результата: «маршрут работает, Flash/medium запрошены, фактический effort сервисом не раскрыт». Не выдавать этот ограниченный вердикт за полную верификацию требования о модели.

Auth route проверяется независимо; при неизвестном или неожиданном способе авторизации/списания нельзя подтвердить обещание подписочного маршрута. При отсутствии допустимого live-аккаунта соответствующий маршрут остаётся `BLOCKED`; чужой backend не подставляется для получения зелёного отчёта.

Выпускной вердикт требует: все применимые P0 прошли; качество соответствует заранее закреплённым порогам; долгий номинальный прогон не теряет chunks; ошибки сохраняют audio и честный статус; есть доказательства установленной сборки на заявленных ОС. P1 без результата либо исправляются, либо явно ограничивают заявленную поддержку.

### Формат результата каждого кейса

Использовать статусы `NOT_RUN`, `PASS`, `FAIL`, `BLOCKED`, `NOT_OBSERVABLE`, `ABORTED`. `NOT_OBSERVABLE` не означает успешную верификацию требования.

Для каждого case/run сохранить:

- ID и уровень D/C/L/E, сборку/ОС/версии CLI, profile hash, active config;
- fixture hash, sample count, длительность, track и meeting IDs;
- ожидаемый результат, наблюдаемое поведение, статус, причина расхождения;
- requested/CLI-reported/provider-confirmed model и effort;
- разрешённые metadata auth/usage без credentials;
- WAV/terminal/trace/SQLite snapshot/export/UI evidence и ссылки на них;
- измерения качества, времени, очереди и процессов;
- дефект с минимальным воспроизведением и перечень непокрытых веток.

Пример полей манифеста будущего runner; это спецификация, а не уже работающий инструмент:

```json
{
  "caseId": "A01",
  "level": "L",
  "status": "NOT_RUN",
  "buildCommit": "b86893651f935e8eb151a8316701687da781d705",
  "route": "porch",
  "porchCommit": "b0c5cf4d5d236677595a508ee3491d56ae1e0e8a",
  "profileId": "agy-gemini-3.8-flash",
  "fixture": {"id": "R02-edge", "sha256": null, "sampleRate": 16000, "samples": 32000},
  "requested": {"model": "gemini-3.8-flash", "effort": "medium"},
  "cliReported": {"model": null, "effort": null},
  "providerConfirmed": {"model": null, "effort": null},
  "counts": {"appJobs": 0, "cliStarts": 0, "modelTurns": null},
  "evidence": [],
  "limitations": []
}
```

Итоговый отчёт должен давать отдельный вердикт для direct agy и Porch, каждой проверенной ОС и максимальной длительности. Перечислить реальные live-прогоны, контролируемые сбои, недоступные наблюдения и непроверенные сценарии. Сохранённый исходник, успешная сборка и mock-тесты не заменяют эти результаты.
